CPU 虚拟化实验 · 任务一 · CPU 共享

一个 CPU，两个计算进程

本实验比较两种条件：A 单独计算，以及 A、B 在同一个逻辑 CPU 上计算。每个进程的计算量相同，比较它们的完成进度、耗时和最终结果。

第二种条件不等 A 结束就启动 B，两个进程的运行时段重叠，称为并发运行。同一个逻辑 CPU 在同一时刻只能执行一个线程；A、B 都是单线程进程，通过调度轮流执行。

每个进程：24 段相同计算每段：4,000 万次迭代单独与并发运行：绑定同一个 CPU
准备程序记录说明实验步骤实测对照机制解释程序说明

准备程序并选择 CPU

下载 参考程序 cpu-sharing-work.c，放到 Ubuntu 的实验目录。需要已有的 GCC、Python 3 和 taskset；原生 Ubuntu 与 WSL Ubuntu 均可运行。

在这个目录的 Bash 终端执行以下命令。后续实验也使用同一个终端：

gcc -std=c11 -O2 -Wall -Wextra -Wpedantic -Werror cpu-sharing-work.c -o cpu-sharing-work
CPU=$(python3 -c 'import os; print(min(os.sched_getaffinity(0)))')
printf 'Selected CPU: %s\n' "$CPU"
编译
第一行把源码编译成可运行的 cpu-sharing-work 程序。
选择 CPU
第二行把一个允许使用的逻辑 CPU 编号保存到变量 CPU 中，第三行显示这个编号。后续的 taskset -c "$CPU" 将各次运行限制在同一个逻辑 CPU 上；它不会排除其他系统进程使用这个 CPU。

先了解进度记录

程序连续执行 24 段计算，不主动休眠。启动时输出一条记录，每完成一段再输出一条，共 25 条。每一行都是一条 JSON 格式的记录，保存这些记录的文件使用 .jsonl 后缀。

字段含义
name本次运行的名称 A 或 B。名称不影响计算量。
batch已完成的段数。0 表示开始，24 表示全部计算完成。
wall该进程从开始到这条记录的经过时间，单位为秒。它包括计算和等待 CPU 的时间，不是 CPU 实际为该进程执行指令的时间。
timestamp同一系统的单调时钟读数，单位为秒，用于比较不同进程的记录先后；它不是日历时间。
checksum当前计算结果的校验值。在本程序中，相同计算量、相同已完成段数应得到相同值。

比较每个进程的完成耗时，使用最后一条记录的 wall；判断 A、B 的运行时段是否重叠，使用 timestamp，不能比较各自从零开始的 wall。

实验步骤

先运行一个计算进程，再运行两个。两种条件下都使用默认计算量，不更改程序参数。

1. 运行 A，记录单进程的完成耗时

taskset -c "$CPU" ./cpu-sharing-work A | tee solo.jsonl

A 是输出中的名称。tee 把记录显示在终端，同时保存到当前目录的 solo.jsonl 文件。

观察什么

  • 记录中的 batch 是否从 0 增加到 24？
  • 查看最后一条记录的 wall 和 checksum，分别得到完成耗时和最终校验值。

参考结果

本次参考运行完成了 24 段计算，耗时约 0.706 秒，最终校验值为 5470079412014018561。你的耗时可以不同；使用默认计算量时，最终校验值应相同。

2. 不等 A 完成就启动 B，比较完成结果

运行以下整组命令，分别保存 A、B 的记录：

taskset -c "$CPU" ./cpu-sharing-work A > pair-a.jsonl &
PID_A=$!
taskset -c "$CPU" ./cpu-sharing-work B > pair-b.jsonl &
PID_B=$!
wait "$PID_A"
wait "$PID_B"
tail -n 1 solo.jsonl pair-a.jsonl pair-b.jsonl
> 与行末的 &
> 将输出写入指定文件，不显示在终端；& 让命令在后台运行，终端不等待 A 完成就可以启动 B。tee 和 > 都会覆盖同名旧文件。
PID_A=$! 与 PID_B=$!
分别保存刚启动的后台进程编号。
wait
等待已启动的 A、B 完成。两个进程都在 wait 之前启动，先等待 A 不会推迟 B 的启动。
tail -n 1
显示三个文件各自的最后一条记录，文件中的其他记录仍然保留。

观察什么

  • 比较三个文件的末行：batch 是否都为 24，checksum 是否相同？
  • 比较 solo.jsonl 与 pair-a.jsonl 的 wall：A 加入这组并发运行后，完成耗时如何变化？再看 B 的完成耗时。

参考结果与原因

单独运行的 A 与并发运行的 A、B 都完成了相同计算，最终校验值一致。并发条件下，A、B 各自耗时约 1.4 秒，A 的耗时约为单独运行的 1.98 倍。

每个进程的计算量没有减少，但两个进程需要轮流使用同一个 CPU，经过时间中包含等待 CPU 的时间。接近两倍是本次测量结果，不是每次运行的固定比例。

3. 按共同时间排列记录，核对两者的进度

最后一条记录能说明计算完成，却不能说明两者何时开始、怎样推进。将并发运行的记录按 timestamp 排序，比较开始和完成的先后：

python3 - <<'PY'
import json
from pathlib import Path
events = [json.loads(line) for name in ('pair-a.jsonl', 'pair-b.jsonl')
          for line in Path(name).read_text().splitlines()]
events.sort(key=lambda event: event['timestamp'])
start = events[0]['timestamp']
for event in events:
    print(f"{event['timestamp'] - start:.3f}s  {event['name']}  {event['batch']:2}/24")
PY

观察什么

  • B 的 0/24 记录是否出现在 A 的 24/24 记录之前？
  • 在第一个进程完成 24 段之前，是否已经出现 A、B 各自完成若干段的记录？

参考结果与原因

参考记录中，B 在 A 完成前开始，两者都在另一方完成前推进了计算。它们不需要等对方全部完成才获得 CPU。

这些记录只标记每段计算的完成时刻，不能确定中间的每次调度切换。若 A 已经完成才启动 B，本次没有形成所需对照；应使用更大的相同计算量重新进行两种运行。

这些对照说明了什么


两个进程轮流使用 CPU
并发记录中，A、B 都在另一方完成之前推进了计算。一个进程尚未完成全部计算时，另一个进程就可以通过调度获得 CPU。
进程切换时，操作系统保存恢复执行所需的状态。进程再次获得 CPU 后，可以继续原来的计算。这是两个进程最终都能完成计算的机制基础。
共享 CPU 不会减少计算量
每个进程仍执行 24 段相同计算，最终校验值一致。加入第二个进程后，各自的经过时间还包含等待 CPU 的时间，因此通常更晚完成。
CPU 虚拟化中的时间共享，就是通过调度让多个进程各自继续执行，共用有限的 CPU 执行时间。并发不意味着单个 CPU 能在同一时刻执行两个线程。


进一步比较：等 A 完成再启动 B


在同一个 Bash 终端中执行以下两条命令。第一条结束后，第二条才会启动 B：


taskset -c "$CPU" ./cpu-sharing-work A > sequential-a.jsonl
taskset -c "$CPU" ./cpu-sharing-work B > sequential-b.jsonl


比较 sequential-b.jsonl 中 batch 为 0 的 timestamp 与 sequential-a.jsonl 中 batch 为 24 的 timestamp：B 的开始应在 A 完成之后。再与步骤 3 的并发记录对照，确认区别在于启动顺序，而不是每个进程的计算量。


顺序运行和并发运行都完成两份计算。并发的特点是两者都能在另一方完成前开始推进，不是单个 CPU 的计算能力翻倍。






程序说明


程序执行固定的 24 段整数计算，计算结束后自动退出。运行格式为 ./cpu-sharing-work NAME [ITERATIONS_PER_BATCH]，方括号表示可选参数，实际命令不输入方括号。


NAME：记录名称
必填，只使用 ASCII 字母、数字、下划线或短横线。例如 A、B；它不改变计算内容。
ITERATIONS_PER_BATCH：每段迭代次数
可选，默认为 40,000,000，整数范围为 1 至 1,000,000,000。修改后，每个进程仍执行 24 段，但每段计算量改变。


以下帮助命令在 Bash 中执行：


./cpu-sharing-work --help


例如 taskset -c "$CPU" ./cpu-sharing-work A 80000000 将每段迭代次数改为 8,000 万。调整计算量后，单独运行的 A 和并发运行的 A、B 都必须使用这个相同参数，重新生成全部记录；最终校验值也应以新计算量为准。
