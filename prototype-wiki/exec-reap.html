程序替换与进程回收

上一个任务用 fork() 创建了子进程。这次让子进程装入另一个程序：执行的程序换了，进程编号会不会也换？子进程已经退出，父进程为什么还要等待它？

进程编号称为 PID。exec 系列接口替换调用进程的程序映像，也就是它执行的代码和程序内存内容；waitpid() 用来等待指定子进程，并收集退出状态。下面用成功和失败两次运行，观察它们分别改变了什么。

两次都相同
父进程创建一个子进程。子进程尝试替换程序；父进程先观察子进程退出后的状态，再用 waitpid() 回收。
两次的区别
第一次使用编译好的目标程序，第二次使用不存在的目标路径。
准备程序比较程序替换比较退出与回收过程与原因判断退出码程序说明

准备两个程序

下载 参考程序 exec-reap-work.c 和 目标程序 exec-reap-target.c，放到 Ubuntu 的同一个实验目录。需要已有的 GCC，不需要绑定 CPU 或管理员权限。

gcc -std=c11 -O2 -Wall -Wextra -Wpedantic -Werror exec-reap-work.c -o exec-reap-work
gcc -std=c11 -O2 -Wall -Wextra -Wpedantic -Werror exec-reap-target.c -o exec-reap-target

后续命令仍在这个目录的 Bash 终端中执行。参考程序创建子进程并记录整个过程；目标程序输出自己的 PID 和变量初值 300，随后以退出码 7 结束。

退出码是程序结束时返回的整数，用来说明结束结果。目标程序的 value 为 300，退出码为 7，二者含义不同。

成功装入目标程序，与找不到目标程序有什么不同？

两次程序都自动完成。下面的参考记录来自 Ubuntu 实测，PID 每次可能不同；只比较同一次运行中的 PID，不要拿两次运行的编号判断是否发生替换。

第一次运行 · 目标程序存在

1. 成功装入目标程序

./exec-reap-work replace

比较 before exec 与 target 两行：PID 是否相同？原程序与目标程序各自的 value 是多少？再查找是否出现 after failed exec。

参考输出

before exec: pid=25621 value=100
target: pid=25621 value=300
target: exit=7
before waitpid: pid=25621 state=Z
waitpid: pid=25621 exit=7
after waitpid: pid=25621 /proc entry=absent
second waitpid: ECHILD

原程序与目标程序输出相同 PID。目标程序从自己的初值 300 开始执行，原程序没有继续输出 after failed exec。替换发生在原来的子进程中，没有再次创建一个进程。

第二次运行 · 目标路径不存在

2. 找不到目标程序

./exec-reap-work missing

当前目录中不能存在 exec-reap-no-such-target。观察有没有 target 输出；再看 after failed exec 的 PID 和变量值。

参考输出

before exec: pid=25661 value=100
exec failed: ENOENT
after failed exec: pid=25661 value=100
child: exit=127
before waitpid: pid=25661 state=Z
waitpid: pid=25661 exit=127
after waitpid: pid=25661 /proc entry=absent
second waitpid: ECHILD

ENOENT 表示目标路径不存在。原程序仍然执行，PID 和变量值都不变。exec 失败后返回错误，并没有自动结束进程；退出码 127 是参考程序随后主动选择的。

子进程已退出，父进程还要回收什么？

继续看刚才两次运行的后四行。子进程退出与父进程收集退出状态是先后两个步骤：

  1. 回收前：before waitpid 中的 state 是 Z。Z 称为僵尸状态：程序已不再执行，内核仍保存退出状态等记录，等待父进程收集。
  2. 调用 waitpid()：waitpid 那一行的 PID 是返回的子进程编号，exit 是从退出状态中取得的退出码。第一次为 7，第二次为 127。
  3. 回收后：after waitpid 的 /proc entry=absent 表示紧接着检查时，该 PID 的进程记录目录已不存在。second waitpid 得到 ECHILD，表示没有可等待的对应子进程，不能把同一份退出状态取两次。

本实验调用 waitpid() 时，子进程已经退出，因此可以直接收集退出状态。如果子进程还没有退出，就调用本实验使用的等待接口，父进程会暂停执行，直到指定子进程退出。

Z 状态不是程序还在计算

子进程退出时会释放程序内存等资源。保留的是退出记录，不是整个程序仍在运行。父进程通过等待接口取得退出状态，内核随后移除这份记录；只是让时间过去，不会代替父进程完成这个动作。

PID 可以被后续新进程重新使用。这里的目录检查针对本次回收后的紧接观察，不表示该编号永远不会再次出现。

程序替换、退出和回收分别改变什么？

成功替换后，进程使用目标程序的代码和内存，从目标程序的入口开始执行。失败时，原程序还在，调用处返回错误。无论替换是否成功，子进程随后都可以退出，而父进程仍需要收集它的退出状态。

退出码是 7，能说明 exec 失败了吗？


第一次运行中，父进程取得退出码 7，而不是 0。有人据此认为目标程序没有成功装入。哪些输出可以支持或反驳这个判断？父进程得到的 7，是目标程序的变量值吗？


参考答案
不能只用退出码判断 exec 是否成功。第一次运行已经有 target 的输出，PID 与替换前相同，原程序也没有继续输出 after failed exec，说明目标程序已经装入并执行。7 是目标程序明确设定的退出码。
目标程序的变量值是 300。父进程收到的是退出码 7，不是变量 value 的内容。与上一个任务相同，等待子进程不会把它的普通私有变量传给父进程。






程序说明


参考程序记录子进程替换程序、退出和被回收的过程。运行格式为 ./exec-reap-work MODE，把 MODE 替换为下面的模式，不需要其他输入。


replace
装入当前目录的 exec-reap-target。目标程序的变量初值是 300，退出码是 7。
missing
尝试装入不存在的 exec-reap-no-such-target。替换失败后，原程序继续输出并以 127 退出；若该路径已存在，参考程序会拒绝运行。
--help
显示用法，不创建子进程。


./exec-reap-work --help


程序先输出子进程的记录，再输出回收前状态、等待结果与回收后检查，随后自动结束。PID 每次可能不同。参考程序自身成功完成观察时返回 0，即使实验中的子进程退出码是 7 或 127。


replace 如果也显示 ENOENT，请检查两份源码是否都已编译，以及终端是否仍在程序所在目录。缺少参数、未知模式或多余参数会显示用法并返回失败。
