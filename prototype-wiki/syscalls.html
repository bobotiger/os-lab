系统调用与内核控制

一个程序打印了 OS 并正常结束，能说明它的每一次读写都成功了吗？任务四的子进程能够装入目标程序，内核究竟接受了什么请求；目标路径不存在时，又怎样把错误交回原程序？

系统调用是用户程序请求内核服务的接口。strace 记录调用名称、参数和结果。这次先跟踪文件读写，再跟踪任务四的进程创建与程序替换，用这些记录判断每个请求实际完成了什么。

读写条件
文件含 O、S 和换行，共 3 字节。程序每次最多读取 8 字节，读完后关闭文件，再用已关闭的编号发起读写。
替换条件
使用任务四的两个程序，分别尝试装入已编译的目标程序和不存在的目标路径。
要区分的事
请求进入内核、请求成功或失败、调度器切换进程，是含义不同的事件。
准备程序读写请求创建与替换进入内核与返回改变文件大小程序说明

准备程序与 3 字节样本

在 Ubuntu 的 Bash 终端中运行 strace -V，确认已有 strace。下载 读写程序 syscall-work.c、任务四参考程序 和 任务四目标程序，放在同一个实验目录。需要已有 GCC；跟踪自己启动的程序不需要管理员权限。

gcc -std=c11 -O2 -Wall -Wextra -Wpedantic -Werror syscall-work.c -o syscall-work
gcc -std=c11 -O2 -Wall -Wextra -Wpedantic -Werror exec-reap-work.c -o exec-reap-work
gcc -std=c11 -O2 -Wall -Wextra -Wpedantic -Werror exec-reap-target.c -o exec-reap-target
printf 'OS\n' > syscall-input.txt

已完成任务四，可以沿用原有两个可执行程序。样本与后面的跟踪文件会覆盖同名旧文件，请在自己的实验目录中执行。后续命令都在这个目录运行。

下面的参考记录来自 WSL Ubuntu-22.04、strace 5.16 的实际运行。PID、文件描述符、路径和地址可能不同，比较同一次运行中相互对应的记录，不要求编号与参考记录相同。

读到数据、读到文件末尾，与读取失败有什么区别？

文件描述符（fd）是进程用来访问已打开文件或通道的编号，不是进程编号 PID。标准输出通常使用 fd 1；本次打开样本得到 fd 3。

strace -f -y -e trace=openat,read,write,close -o io.trace ./syscall-work syscall-input.txt
cat io.trace

程序在终端输出 OS 和换行。跟踪记录保存在 io.trace；-y 为有效文件描述符标出路径。先找到打开 syscall-input.txt 的 openat 行，再沿它返回的编号查找读取和关闭，避免把装入共享库时的读取当成样本读取。

样本读写的实际记录摘录

34974 openat(AT_FDCWD</tmp/oslab-syscalls-tuoROL>, "syscall-input.txt", O_RDONLY) = 3</tmp/oslab-syscalls-tuoROL/syscall-input.txt>
34974 read(3</tmp/oslab-syscalls-tuoROL/syscall-input.txt>, "OS\n", 8) = 3
34974 write(1</dev/pts/6>, "OS\n", 3)   = 3
34974 read(3</tmp/oslab-syscalls-tuoROL/syscall-input.txt>, "", 8) = 0
34974 close(3</tmp/oslab-syscalls-tuoROL/syscall-input.txt>) = 0
34974 read(3, 0x7ffe713dba70, 8)        = -1 EBADF (Bad file descriptor)
34974 write(3, "X", 1)                  = -1 EBADF (Bad file descriptor)

每行开头的 34974 是调用者 PID。AT_FDCWD 表示相对当前工作目录打开文件，尖括号内是 strace 解码的路径；/dev/pts/6 是这次运行的终端。记录中的 \n 表示一个换行字节。

分别圈出每次 read、write 的请求字节数与返回值，再看 close 在哪里。哪些请求取得了数据，哪些只是没有更多数据，哪些使用的编号已经无效？

第一次 read：8 与 3
8 是最多想读的字节数，3 是实际读到的字节数。文件只有 3 字节，返回少于请求大小不表示失败。
write 到标准输出：3 与 3
请求写入 3 字节，返回 3，表示这次写入接受了这 3 字节。这里的 fd 是 1，不是样本文件的 3。
第二次 read：返回 0
样本的 3 字节已读完，当前文件位置到达末尾。0 表示没有更多数据，不是错误。
close 之后：两次 EBADF
fd 3 已被关闭，不能再用它读写。内核拒绝请求，返回 -1，并给出无效文件描述符错误；X 没有被写入。

缓冲区是程序提供的一段内存，用来接收读入的数据。成功的 read 记录在引号中显示已读数据；失败的 read 可能只显示这段内存的地址，不代表已经读入了数据。write 的引号则显示程序请求写入的内容。

程序能正常结束，是因为它处理了预期的错误，不代表每一次系统调用都成功。

谁创建了子进程，谁请求装入目标程序？

继续使用任务四的程序。-f 同时跟踪子进程；%process 选择进程相关调用，write 保留程序输出对应的写入记录。两次运行的 PID 不同，要在各自的文件中比较。

目标程序存在

strace -f -e trace=%process,write -o replace.trace ./exec-reap-work replace
cat replace.trace

找出创建调用返回的子进程 PID，再找该 PID 的 execve 和 target 输出。目标程序装入后，这个 PID 是否改变？

创建与替换的实际记录摘录

34978 clone(child_stack=NULL, flags=CLONE_CHILD_CLEARTID|CLONE_CHILD_SETTID|SIGCHLD, child_tidptr=0x7e6a58a6aa10) = 34979
34979 write(1, "before exec: pid=34979 value=100"..., 33) = 33
34979 execve("./exec-reap-target", ["./exec-reap-target"], 0x7ffeb3c91b20 /* 22 vars */) = 0
34979 write(1, "target: pid=34979 value=300\ntarg"..., 43) = 43

父进程 34978 的创建调用返回 34979，随后子进程 34979 请求装入目标程序。成功后，target 的输出仍来自 34979，没有因为 exec 再创建一个进程。

目标路径不存在

strace -f -e trace=%process,write -o missing.trace ./exec-reap-work missing
cat missing.trace

当前目录不能存在 exec-reap-no-such-target。找出 execve 的错误，再查看 after failed exec 的写入来自哪个 PID。

创建与替换的实际记录摘录

34983 clone(child_stack=NULL, flags=CLONE_CHILD_CLEARTID|CLONE_CHILD_SETTID|SIGCHLD, child_tidptr=0x71756d640a10) = 34984
34984 write(1, "before exec: pid=34984 value=100"..., 33) = 33
34984 execve("./exec-reap-no-such-target", ["./exec-reap-no-such-target"], 0x7ffd94583e80 /* 22 vars */) = -1 ENOENT (No such file or directory)
34984 write(1, "exec failed: ENOENT\n", 20) = 20
34984 write(1, "after failed exec: pid=34984 val"..., 55) = 55

创建子进程成功，但装入程序失败：路径不存在，返回 -1 ENOENT。原程序仍由 34984 执行，可以处理错误并输出 after failed exec。

fork 与 clone
fork 是程序使用的接口；本次 x86-64 Ubuntu 的底层创建请求显示为 clone。其他环境可能显示 clone3 或 fork，应依据调用者和返回 PID 判断创建关系。
exec 与 execve
exec 系列接口的装入请求显示为 execve。参数包含目标路径、程序参数列表和环境变量地址；/* 22 vars */ 表示这次传入的环境变量数量，不是退出码。
成功的 0 与退出码 7
strace 用 execve 的 = 0 显示装入成功；原程序不会继续执行 exec 后面的语句。目标程序后来的退出码 7 是它的结束状态，不表示装入失败。
怎样辨认记录中的其他行？

最开始装入 exec-reap-work 的 execve，是 strace 启动被跟踪程序，不是子进程的替换请求。程序的退出与等待记录仍可按任务四的方法辨认。

unfinished 与 resumed 可能将一次调用分成两行显示：先记录进入，随后补上返回。应按同一 PID 和调用名称配对，不要数成两次调用，更不能把记录的行序当成 CPU 调度时间线。

write 中的省略号表示字符串显示被截短，不表示只写了可见的部分；返回值给出这次实际接受的字节数。

进入内核后，调用进程发生了什么？

用户态限制普通程序直接操作受保护的系统资源；内核态允许内核执行这些操作。系统调用让 CPU 进入内核态，处理调用进程的请求。对下面这些 read、write 请求，无论成功还是失败，结果都返回调用它的进程。

一次系统调用的三个阶段

  1. 1. 用户态 · PID 34974

  2. 2. 内核态 · 处理请求

  3. 3. 用户态 · PID 34974

对应的实际记录



进入内核是执行权限与执行位置的变化，不是创建了一个“内核进程”。调度器选择另一个进程执行，才是进程切换；如果一次读取需要等待数据，调用进程可能阻塞，调度器可以让其他进程执行。


相同 PID 能说明这些请求属于同一进程，不能证明它在两行记录之间一直占用 CPU。既不能把每一行系统调用数成一次进程切换，也不能据此认定期间完全没有切换。exec 成功的情形则是同一进程开始执行新程序，而不是返回原程序继续。






文件变成 9 字节，第二次 read 还会返回 0 吗？


不改变程序和每次最多读取 8 字节的条件，另建一个含 OS123456 和换行的文件，共 9 字节。先判断两次 read 应各返回多少，再按新文件路径找到记录核对。


printf 'OS123456\n' > syscall-long.txt
strace -f -y -e trace=openat,read,write,close -o long.trace ./syscall-work syscall-long.txt
cat long.trace


参考结果与原因
第一次 read 取得 OS123456，共 8 字节，返回 8；文件位置向后移动 8 字节。第二次仍有一个换行字节，返回 1，不是 0。两次都没有失败。
程序只将第一次读到的数据写到标准输出，因此终端显示 OS123456，没有换行；第二次读到的换行应在跟踪记录中核对。返回值取决于实际取得的数据量，而不是必须等于请求上限，也不是“第二次读取就一定到末尾”。
关闭描述符之后的两次 EBADF 仍然出现。文件内容变多，不会使已关闭的描述符重新有效。






程序说明与 strace 选项


读写程序格式为 ./syscall-work FILE。FILE 是可读取的文件路径，本任务先使用 syscall-input.txt。程序读最多 8 字节，向标准输出写出第一次取得的数据，再读一次，关闭文件，检查关闭后的读写错误，然后自动结束。


FILE
可以使用当前目录的文件名，也可以使用完整路径。3 字节样本使第二次读取到达末尾；文件超过 8 字节时，第二次仍可能取得数据。
--help
显示用法，不执行文件读写实验。
输出与结束结果
标准输出只显示第一次读取的数据。找不到文件或出现非预期读写错误时程序返回失败；预期的两次 EBADF 正确出现时返回 0。


./syscall-work --help


strace 用法
基本格式为 strace [选项] 程序 [程序参数]。strace 先启动指定程序，再把符合条件的系统调用记入跟踪文件。


-f
跟踪本次启动的进程及其子进程；任务四的替换发生在子进程中。
-y
为有效文件描述符显示关联路径，便于区分样本、共享库与标准输出。
-e trace=...
只显示指定调用；本任务的 %process 表示进程相关调用组。
-o FILE
将跟踪记录写入 FILE；终端仍显示程序自己的标准输出。cat FILE 查看完整记录。


任务四程序的 replace、missing 参数保持原用法。若 strace 提示没有跟踪权限，应先核对运行环境的安全策略，不能把跟踪权限错误当成样本程序的读写失败。strace 会干预被跟踪程序的执行，这些运行的耗时不用于与任务一测量比较。
