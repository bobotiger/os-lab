计算、等待与暂停：观察进程状态

本实验在 Ubuntu 中观察进程的三种状态：可以执行计算、等待数据、被信号暂停。每次只改变一个条件，再比较改变前后的状态记录。

运行参考程序后，终端中的控制程序会创建两个进程 A、B：

进程 A
启动后持续执行计算。
进程 B
启动后等待管道中的数据，收到一个字节后开始持续计算。

管道是进程之间传递数据的通道。本实验把一个字节的数据作为通知，用来让 B 开始计算。

A、B 使用同一个逻辑 CPU。实验过程中，可以单独暂停和恢复 A，B 的计算或等待条件不受这些命令影响。

准备程序并启动

下载 参考程序 process-state-work.c，放到 Ubuntu 的实验目录。需要已有的 GCC、Python 3 和 taskset，不需要管理员权限。

在这个目录的 Bash 终端中执行以下命令：

gcc -std=c11 -O2 -Wall -Wextra -Wpedantic -Werror process-state-work.c -o process-state-work
CPU=$(python3 -c 'import os; print(min(os.sched_getaffinity(0)))')
taskset -c "$CPU" ./process-state-work
编译
第一行把参考源码编译成可运行的 process-state-work 程序。
选择 CPU
第二行把一个允许使用的逻辑 CPU 编号保存到变量 CPU 中。第三行用 taskset 将程序限制在这个 CPU 上，程序创建的 A、B 也继承此限制。

启动后会显示两个进程的编号，以及等待输入的提示符：

READY A=7779 B=7780
Commands: observe / send / stop / resume / quit
state>

这里的编号只是示例，以你实际得到的编号为准。出现 state> 后，输入的是本实验程序的命令；只有退出程序后，终端才重新接受 Bash 命令。

先了解输出中的状态和时间

observe 观察约一秒，再分别输出 A、B 的记录。每次输出中，一个进程对应一行。

输出字段含义
NAME进程名称 A 或 B。
PID进程编号。同一轮实验中不变；重新启动后，以新的 READY 输出为准。
BEFORE观察开始时的状态。
AFTER观察结束时的状态。以下步骤主要比较这一列。
CPU_DELTA(s)本次观察中，CPU 为该进程执行指令所用的时间，单位为秒。例如 0.530 表示用了 0.530 秒 CPU 时间。
elapsed本次观察实际经过的秒数，通常略大于一秒。

CPU 时间不包含进程等待数据或等待分配 CPU 的时间。它与实际经过的时间不是同一个数值。

状态Linux 中的含义本实验中的条件
R正在运行，或已经就绪、等待 CPU。进程有计算可做，并且没有被暂停。
S可被信号中断的睡眠。B 的管道中没有数据，读取操作正在等待。
T被暂停。A 收到了 SIGSTOP 暂停信号。

R 不保证采样的那个瞬间正在执行。判断一个进程是否在观察期间用过 CPU，还要看 CPU_DELTA(s) 是否大于零。0.000 表示本次采样没有记录到它使用 CPU 的时间。

实验步骤

从刚启动的状态开始，按以下顺序操作。每个步骤先比较记录，再结合参考解释核对原因。

1. 不发送通知，观察 B 的等待状态

此时 A 持续计算，B 的管道中没有数据。先不改变任何条件，连续观察两次：

observe
observe

观察什么

  • 在每次输出中，比较 A、B 两行的 AFTER 列和 CPU_DELTA(s) 列。
  • 两次观察之间没有发送数据。B 的状态和 CPU 时间读数是否保持一致？

参考结果与原因

观察结束时，A 的状态为 R，CPU 时间大于零；B 的状态为 S，CPU 时间为 0.000 秒。

B 正在等待管道中的数据，不能执行读取之后的计算。再等一秒并不会产生数据，所以第二次观察时它仍然等待。

2. 发送通知，观察 B 开始计算

只改变 B 的数据条件，A 仍然持续计算。send 向管道写入一个字节，随后再观察：

send
observe

观察什么

  • 比较上一步与本次观察的 AFTER 列，B 的状态是否从 S 变为 R？本次使用的 CPU 时间是否大于零？
  • A 那一行的 CPU 时间是否也大于零？

参考结果与原因

观察结束时，A、B 的状态均为 R，两者在本次观察中都用过 CPU。

管道有了数据，B 的读取操作可以完成，它随后进入计算。A、B 使用同一个逻辑 CPU，通过调度轮流执行；两行都有 CPU 时间，不表示两个进程在同一时刻执行指令。

3. 暂停 A，观察 B 是否继续计算

保持 B 的计算不变。stop 只向 A 发送 SIGSTOP 暂停信号：

stop
observe

观察什么

  • 观察结束时，A 的状态是否为 T？CPU 时间是否为零或接近零？
  • B 的状态是否仍为 R？CPU 时间是否仍大于零？

参考结果与原因

观察结束时，A 的状态为 T：它已被暂停，不再执行计算。B 没有收到暂停信号，继续计算。

A 的暂停与等待管道数据不同：即使还有计算可做，暂停期间也不能执行。它需要继续信号才能恢复。

4. 恢复 A，观察它是否重新计算

resume 只向 A 发送 SIGCONT 继续信号，不给 B 发送新的数据：

resume
observe

观察什么

  • 观察结束时，A 的状态是否重新为 R？本次使用的 CPU 时间是否大于零？
  • 比较暂停前、暂停后和恢复后的 PID 列，A 的进程编号是否相同？

参考结果与原因

A 恢复后继续计算，再次与 B 共享 CPU。恢复没有创建新的进程，因此 A 的 PID 没有变化。

5. 退出程序，结束两个计算进程

quit

程序终止并回收 A、B，显示 DONE: A and B terminated and reaped.，然后返回 Bash 终端。

程序不会因完成一次观察而自动退出。完成实验后应执行 quit；关闭标准输入或按 Ctrl+C 也会清理子进程。

状态变化取决于什么条件

本实验中的状态为什么不能继续计算如何继续
B 等待数据：S管道中没有数据，读取操作不能完成。向管道写入数据，使读取操作能够完成。
A 被暂停：T暂停信号阻止了执行，即使 A 有计算可做。发送 SIGCONT 继续信号，解除暂停。

这两个状态下都可能得到零 CPU 时间，但继续执行所需的条件不同。给 B 发送数据不会恢复 A；恢复 A 也不会给 B 的管道添加数据。

条件满足后，进程可以重新参与 CPU 调度。是否马上执行、先执行 A 还是 B，由调度决定。

进一步验证：先暂停 A，再给 B 发送通知

先退出上一轮程序，再从 Bash 终端重新启动，恢复 A 计算、B 等待的初始条件：

taskset -c "$CPU" ./process-state-work

在 state> 提示符下执行以下命令：

stop
observe
send
observe
resume
observe
quit

第一次观察：A 被暂停，B 等待数据。第二次观察：B 收到数据后开始计算，但 A 应仍为 T。第三次观察：A 收到继续信号后恢复计算。

通过这个顺序核对两种恢复条件：数据解决 B 的等待，继续信号解决 A 的暂停。

程序说明

process-state-work 在当前终端接收命令，控制两个子进程 A、B。输入格式为每行一个命令，不带参数；结果直接显示在终端，不保存文件。

命令作用
observe观察约一秒，输出两个进程的状态和本次使用的 CPU 时间，不改变计算、数据或暂停条件。
send给 B 的管道发送一个字节，一轮程序中只发送一次。B 开始计算后不会再等待管道。
stop向 A 发送 SIGSTOP 暂停信号。
resume向 A 发送 SIGCONT 继续信号。
quit终止并回收两个子进程，包括仍处于暂停状态的 A。

要重新进行实验，先 quit，再从同一个 Bash 终端启动程序。帮助命令也在 Bash 中执行：

./process-state-work --help

重复 send 会提示通知已发送，不会重新开始 B 的等待。未知命令会显示可用命令列表，不改变当前条件。
