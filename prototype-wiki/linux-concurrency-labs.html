开始实验

使用 Ubuntu 或 WSL 中的 Ubuntu。前三个实验需要 Bash、支持 pthread 的 C 编译器（cc）；第四个需要 Bash 和 Python 3，无需第三方 Python 包。运行脚本还会调用 Ubuntu 中的 timeout，限制单次运行时间。

可下载完整学生包，也可在下面各实验处下载独立运行包。解压后保留目录结构，在包含 run.sh 的目录打开终端。用文本编辑器修改对应的 config.sh 并保存，再运行该实验给出的命令。脚本会读取当前配置，并按需编译 C 源码。

互斥锁

实验一 测出抢座程序的问题

下载本实验运行包（ZIP）

包含本实验源码、配置、运行脚本和使用说明；关键变量与接口调用已有中文注释。

每位买家申请一个座位，成功后得到一张票。你可以设置座位数、买家数，以及查询余票后等待多久才出票。

配置文件：01-seats/config.sh

配置参数

以下列出各参数的初始设置。数值只填整数，时间单位为毫秒；英文选项按表中写法填写，区分大小写。

互斥锁：配置参数
参数与初始设置 取值范围或选项 含义与作用
SEATS=11～16初始座位数。每次启动程序时，余票数都重新设为这个值。
BUYERS=11～16买家数量，也是买家线程数。每位买家只申请一个座位。
GAP_MS=00～1000 毫秒查询余票后、尝试出票前的等待时间。0 表示不额外等待。
ARRIVAL_MS=00～1000 毫秒相邻买家的预设到达间隔。所有线程准备好后，第一个不额外等待，第二个等待一个间隔，第三个等待两个间隔，以此类推。0 表示不主动错开到达时间。
LOCK=splitsplit / wholesplit：查询和出票分别加锁，中间等待时不持锁。
whole：从查询到出票始终持锁，中间的等待也在锁内。

先用 split 运行，再按任务要求与 whole 对照。预设到达时间不等于实际执行时间，操作系统调度仍会影响买家线程的先后顺序。

保存配置后，在包含 run.sh 的解压目录中运行：

bash run.sh seats

操作与结果分析建议

需要完成的任务

  1. 先想清楚：怎样的出票结果才算正确？然后增加买家数、调整到达间隔，或延长出票前的等待。每次只改一个参数，先预测再运行。出现错误时，记下完整配置。
  2. 保持买家数和座位数不变，只调整时间参数，让错误暂时不再出现。再恢复之前的设置，尝试复现错误。比较两次输出中 READ 和 ISSUE 的顺序，解释为什么结果不同。仅凭一次没有出错，能说明 split 的实现一定正确吗？
  3. 让座位数与买家数相等，其余参数仍采用之前容易出错的设置。先预测余票数，再运行核对。初始座位数、出票数和剩余座位数之间应该满足什么关系？用这个关系检查本次结果。
  4. 恢复之前出错的配置，只把 LOCK 改为 whole，切换到程序已提供的另一种加锁方式，再运行一次。根据输出和参数说明，解释不同买家的哪些操作不能再交错执行。随后换一组人数或时间参数，看看结果是否仍然正确。

需要提交的材料

  1. 每次运行前的预测、完整配置和程序输出，涵盖正常运行、复现错误、调整时间使错误消失、恢复原条件，以及切换 whole 后的两组测试。
  2. 选一次出错运行，按 READ 和 ISSUE 的顺序，说明相关买家分别读到了多少余票，以及程序怎样更新余票数。
  3. 用初始座位数、出票数和余票数的关系检查结果，并解释仅调整时间与切换加锁方式有什么区别。

读懂程序输出

READ 表示查询余票，其中 seen 是买家线程读到的余票数；ISSUE 表示出票，REJECT 表示拒绝申请。SUMMARY 中的 capacity、issued、left 分别是初始座位数、出票数和程序记录的余票数。

所有买家线程准备好后，再按预设间隔开始抢座，实际顺序还会受调度影响。保存一次完整输出，按先后顺序梳理每位买家读到了多少余票、是否拿到票，以及程序怎样更新余票数。

条件变量

实验二 通知发出后会发生什么

下载本实验运行包（ZIP）

包含本实验源码、配置、运行脚本和使用说明；关键变量与接口调用已有中文注释。

工作线程等待领取任务，每个线程在一次运行中最多领取一项。主线程负责往队列中放入任务，并通知工作线程。你也可以让它在队列还是空的时候先发通知。

配置文件：02-queue/config.sh

配置参数

以下列出各参数的初始设置。数值只填整数，时间单位为毫秒；英文选项按表中写法填写，区分大小写。

条件变量：配置参数
参数与初始设置 取值范围或选项 含义与作用
WORKERS=11～8工作线程数。每个线程在一次运行中最多领取一项任务。
JOBS=10～8主线程一次放入队列的任务数。0 表示不放入任务。任务数超过线程数时，即使所有线程各取一项，也会有任务剩余。
EMPTY_NOTICE=00 / 10：放入任务前不发通知。
1：队列为空时先广播一次，等待 OBSERVE_MS 毫秒，再放入任务。这次提前通知始终使用广播，不受 NOTICE 影响。
NOTICE=broadcastsignal / broadcast放入任务后的通知方式。
signal：通知一个等待线程。
broadcast：通知所有等待线程。
WAIT=ifif / whileif：等待返回后直接尝试领取任务，不因队列为空而重新等待。
while：每次被唤醒后都重新检查；队列为空且尚未关闭时，继续等待。
OBSERVE_MS=300100～2000 毫秒放入任务后，主线程等待这么久再统计结果。若 EMPTY_NOTICE=1，提前通知到放入任务之间也等待同样长的时间。

NOTICE 控制放入任务后的通知，EMPTY_NOTICE 控制是否提前通知，WAIT 控制工作线程醒来后的行为。三个选项分别起作用。

保存配置后，在包含 run.sh 的解压目录中运行：

bash run.sh queue

操作与结果分析建议

需要完成的任务

  1. 从一个线程、一项任务开始，先增加线程数，再增加任务数。找出会出现 EMPTY_ATTEMPT 和不会出现它的两组配置。增加任务后没有出错，能否说明等待逻辑已经正确？
  2. 恢复默认配置，只把 EMPTY_NOTICE 改为 1。先猜一猜：工作线程收到提前发出的通知后会做什么？等主线程真正放入任务后，还有线程来领取吗？运行程序，检查你的预测。
  3. 分别恢复前两步中出错的配置，只把 WAIT 改为 while，再运行一次。观察线程被唤醒后的行为：如果队列仍然为空，它接下来会做什么？
  4. 设置两个线程、两项任务，保持 WAIT=while、EMPTY_NOTICE=0，比较 signal 和 broadcast。检查两个线程是否各领到一项。如果没有出现空取，但队列里仍有任务，请解释原因。

需要提交的材料

  1. 各组运行前的预测、完整配置和程序输出，包含任务少于线程数、提前通知，以及这两种条件下 if 与 while 的对照。
  2. 两个线程、两项任务时，signal 与 broadcast 的对照结果。记录 taken、queued、empty_attempts，并说明统计结果是在 CLOSE 之前得到的。
  3. 解释线程收到通知后为什么仍需检查队列，以及为什么没有出现空取，也可能有任务无人领取。

看清统计结果和退出过程

WAIT、WAKE、TAKE 分别表示等待、唤醒和领取任务。EMPTY_ATTEMPT 表示线程尝试从空队列取任务，文中简称“空取”。SNAPSHOT 中的 taken、queued、empty_attempts 分别是截至统计时已领取的任务数、剩余任务数和累计空取次数。

输出 SNAPSHOT 后，主线程设置关闭状态，输出 CLOSE，再唤醒仍在等待的线程，让它们退出。关闭后，工作线程不再领取任务。分析结果时，要分清线程没有及时被唤醒、醒来后没有任务可领，以及等待逻辑本身有误这几种情况。必要时延长观察时间再运行。

信号量

实验三 为什么可用资源越来越少

下载本实验运行包（ZIP）

包含本实验源码、配置、运行脚本和使用说明；关键变量与接口调用已有中文注释。

线程必须先取得一个信号量许可，才能使用资源。每轮申请的线程数都等于资源池的初始容量，其中一部分线程可以在取得许可后取消任务。多轮运行共用同一个信号量。

配置文件：03-pool/config.sh

配置参数

以下列出各参数的初始设置。数值只填整数，时间单位为毫秒；英文选项按表中写法填写，区分大小写。

信号量：配置参数
参数与初始设置 取值范围或选项 含义与作用
CAPACITY=21～8信号量的初始许可数。每轮发起申请的线程数也等于这个值；后续轮次不会自动补回缺少的许可。
ROUNDS=31～8一次启动后连续运行的轮数。各轮共用一个信号量；重新启动程序才按 CAPACITY 重新初始化。
CANCEL=00～CAPACITY每轮要取消的任务数。按取得许可的先后顺序，前 CANCEL 个成功申请的线程取消任务。成功申请数不足时全部取消；0 表示不取消。
WORK_MS=1000～500 毫秒取得许可后的模拟处理时间。所有线程尝试申请后，成功取得许可的线程都会等待这么久，包括随后取消任务的线程。0 表示不额外等待。
CLEANUP=leakleak / returnleak：正常完成时归还许可，取消任务时不归还。
return：无论正常完成还是取消任务，只要取得过许可，就会归还。

CANCEL 只作用于已经取得许可的线程。申请失败的线程不会取消任务，也不会归还自己没有取得的许可。

保存配置后，在包含 run.sh 的解压目录中运行：

bash run.sh pool

操作与结果分析建议

需要完成的任务

  1. 先不取消任务，记录每轮结束时还有多少可用许可。然后增加 CANCEL，预测许可会在哪一轮用完，再增加运行轮数进行验证。保存从正常处理请求到所有申请都失败的完整输出。
  2. 保持 CANCEL 不变，只增大 CAPACITY。先预测：增加容量能解决问题，还是只能让问题晚些出现？再用运行结果检验你的判断。
  3. 保持 CANCEL 和 CAPACITY 不变，把 WORK_MS 减为零。缩短等待后，每轮结束时的可用许可数恢复了吗？结合输出，区分许可暂时被线程占用与线程结束后没有归还许可。
  4. 恢复之前出错的配置，只把 CLEANUP 改为 return，再运行一次。随后把 CANCEL 设为 CAPACITY，让所有取得许可的线程都取消任务，检查每轮结束后是否还有许可未归还。

需要提交的材料

  1. 各组运行前的预测、完整配置和程序输出，包含不取消任务、加入取消操作、增加容量、缩短等待、切换 return，以及全部任务取消的情况。
  2. 逐轮记录开始和结束时的可用许可数、成功申请数、取消数和申请失败数。把预测的许可数与实际结果放在一起比较。
  3. 根据 CANCEL 或 FINISH 行中的归还信息，解释许可为什么减少，并说明增加容量、缩短等待和切换归还方式分别有什么影响。

核对每轮的许可数

ACQUIRE 表示取得许可，EAGAIN 表示本次申请时没有可用许可。CANCEL 和 FINISH 表示取消任务和正常完成，所在行还会注明是否归还许可。所有工作线程结束后，主线程统计可用许可数，并在 END 的 available 中给出结果。统计时会临时取走许可，数完后全部归还。

每轮中，所有线程都尝试申请一次后，取得许可的线程才开始等待，并根据所选实现决定是否归还。取消操作通过普通代码分支模拟，不使用 pthread_cancel。请计算每轮结束时应有多少可用许可，再与下一轮开始时的 start_available 比较。

事件驱动

实验四 程序为什么延迟处理快消息

下载本实验运行包（ZIP）

包含本实验源码、配置、运行脚本和使用说明；关键变量与接口调用已有中文注释。

程序通过两条连接接收消息，分别标为 slow 和 fast。你可以推迟 slow 的发送，也可以延长它的处理时间，看看 fast 是否也会延迟处理。

配置文件：04-events/config.sh

配置参数

以下列出各参数的初始设置。数值只填整数，时间单位为毫秒；英文选项按表中写法填写，区分大小写。

事件驱动：配置参数
参数与初始设置 取值范围或选项 含义与作用
SLOW_SEND_MS=00～2000 毫秒程序启动后，预定等待多久发送 slow。0 表示不额外推迟发送。
FAST_SEND_MS=1000～2000 毫秒程序启动后，预定等待多久发送 fast。它与 SLOW_SEND_MS 使用同一个计时起点，并不是相对 slow 的间隔。
SLOW_WORK_MS=00～2000 毫秒开始处理 slow 后额外等待的时间，用来模拟慢处理。0 表示不额外等待。fast 的处理不受这个参数直接控制。
IO=blockingblocking / epollblocking：先阻塞读取 slow，再读取 fast。
epoll：把套接字设为非阻塞，用 epoll 等待可读事件，读取已有数据的连接。
HANDLER=inlineinline / workerinline：接收线程直接处理消息，处理结束后才能继续接收。
worker：把处理交给最多两个工作线程，接收线程继续执行读取操作。

IO 决定怎样读取消息，HANDLER 决定由哪个线程处理消息，两者可以组合。发送时刻可能受调度影响；同时发送时，不预先假定处理顺序。

保存配置后，在包含 run.sh 的解压目录中运行：

bash run.sh events

操作与结果分析建议

需要完成的任务

  1. 先运行默认配置，再只推迟 slow 的发送，让 fast 先到达。逐渐拉大两条消息的发送间隔，预测并记录 fast 从发送到处理结束需要多久。然后只把 IO 改为 epoll，用相同的发送时间再次测量。
  2. 保持 IO=epoll、HANDLER=inline，让 slow 先到、fast 稍后到，再逐步增大 SLOW_WORK_MS。比较 fast 的发送、接收和开始处理时间，并查看 slow 在这段时间内的处理过程。fast 延迟期间，接收线程在做什么？
  3. 保留第二步中使 fast 明显延迟的设置，只把 HANDLER 改为 worker。检查程序能否在 slow 处理结束前完成 fast 的处理，并解释原因。
  4. 保持 HANDLER=worker，把发送时间恢复为第一步中 fast 先到、slow 后到的设置。同时将 SLOW_WORK_MS 设为 0、IO 设为 blocking。先预测使用工作线程能否解决这时的延迟，再运行验证。

需要提交的材料

  1. 每次运行前的预测、完整配置和程序输出，包含慢到达时 blocking 与 epoll 的对照、慢处理时 inline 与 worker 的对照，以及 worker 搭配 blocking 的再次测试。
  2. 从输出中记录 fast 的发送、接收、开始处理和处理结束时间，分别计算接收前与接收后的耗时，并比较不同配置下的变化。
  3. 对照同一时段内 slow 的处理过程，解释 fast 为什么延迟，以及改变读取方式或处理线程分别能解决哪一种等待。

比较两段等待时间

SEND、RECEIVE、HANDLER_START、HANDLER_END 分别表示发送、接收、开始处理和处理结束。它们前面的时间以程序启动为起点。SUMMARY 中的 latency_ms 是从记录发送时刻到处理结束的总耗时。自行设置几组延迟，分别比较 fast 在接收前和接收后的耗时。

消息由独立线程按预设时间发送，实际发送时刻可能因调度而推迟。选择 inline 时，接收线程直接处理消息；选择 worker 时，它把消息交给工作线程处理。本实验用等待来模拟慢处理，解释结果时要说明这一点。
