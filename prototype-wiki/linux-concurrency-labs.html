Linux 并发验证实验

阅读四个验证程序，改变运行条件，再用程序输出解释不同实现的表现。

你必须有一个能运行全部四个验证程序的 Linux 环境。 可以使用 Ubuntu 或 WSL 中的 Ubuntu。

实验一 · 互斥锁测出抢座程序的问题 实验二 · 条件变量通知发出后会发生什么 实验三 · 信号量为什么可用资源越来越少 实验四 · 事件驱动程序为什么延迟处理快消息

运行准备

四项实验都用 Bash。前三项还需要支持 pthread 的 C 编译器（cc），第四项需要 Python 3。

下载完整学生包（ZIP）

包含四个实验的源码、配置、运行脚本和使用说明。各实验也提供独立运行包。

解压后保留目录结构，在含有 run.sh 的目录打开终端。找到对应的 config.sh，修改参数并保存，再运行该实验的命令。配置可以切换程序已有的实现，不要求修改或提交源码。

怎样做对照并判断结果

  1. 找出问题出现的条件

    先用默认配置运行。保持当前实现不变，每次只改一个输入参数。运行前写下预测和判断依据，运行后记下完整配置和相关输出。

  2. 在同一组输入下比较实现

    用出现过问题的配置做对照。保持人数、任务量、延迟等输入不变，只切换实现。对比两次输出中的同一项数据。

  3. 用输出检验判断

    根据实验要求核对结果。例如，抢座实验的出票数加余票数应等于初始座位数。用同一组配置重复运行，再换几组输入。一次输出符合预期，只说明这次没有观察到问题。

线程调度会影响事件的先后和耗时。用输出中的时间戳分析本次运行的经过。

实验一 · 互斥锁

测出抢座程序的问题

每位买家申请一个座位。改变买家人数、到达间隔和查询余票后的等待时间，观察哪些情况下程序会多出票，或者记错余票数。

修改 01-seats/config.sh，保存后运行。

bash run.sh seats
下载互斥锁实验包（ZIP）

配置参数

数值填整数，英文选项按表中写法填写，区分大小写。

互斥锁：配置参数
参数与默认值 允许的取值 作用
SEATS=11～16初始座位数。每次启动程序时，余票数都重新设为这个值。
BUYERS=11～16买家数量，也是买家线程数。每位买家只申请一个座位。
GAP_MS=00～1000 毫秒查询余票后、尝试出票前的等待时间。0 表示不额外等待。
ARRIVAL_MS=00～1000 毫秒相邻买家的预设到达间隔。所有线程准备好后，第一个不额外等待，第二个等待一个间隔，第三个等待两个间隔，以此类推。0 表示不主动错开到达时间。
LOCK=splitsplit / wholesplit：查询和出票分别加锁，中间等待时不持锁。
whole：从查询到出票始终持锁，中间的等待也在锁内。

先用 split 运行，再与 whole 对照。配置里的到达间隔是预设值，实际执行顺序还会受线程调度影响。

操作与结果分析建议

需要完成的任务

  1. 找出会出错的条件

    先写下你认为正确的出票结果。增加买家数、调整到达间隔或延长出票前的等待，每次只改一项。出现错误时，保存完整配置。

  2. 改变时机，再复现错误

    固定座位数和买家数，只改时间参数，让这次运行不再出错。恢复原设置并尝试复现。对照 READ 和 ISSUE 的顺序，解释两次结果为什么不同。

  3. 用数量关系检查结果

    把座位数设为与买家数相同，保留之前容易出错的时间参数。先预测余票数，再用初始座位数、出票数和余票数之间的关系检查实际结果。

  4. 比较两种加锁范围

    恢复出错时的完整配置，只把 LOCK 改为 whole。根据输出解释哪些操作不能再交错。再换一组人数或时间参数，检查结果是否仍符合预期。

读懂程序输出

READ 是查询余票，seen 是该买家读到的数值。ISSUE 表示出票，REJECT 表示拒绝申请。

在 SUMMARY 中查看 capacity、issued、left，分别对应初始座位数、出票数和余票数。按输出顺序追踪每位买家读到多少余票、是否拿到票，以及程序怎样更新余票。

需要提交的材料

  1. 附上各次运行的预测、完整配置和程序输出。包括正常运行、复现错误、调整时间、恢复原设置，以及使用 whole 的两组测试。
  2. 选一次出错运行，依据 READ 和 ISSUE 说明相关买家读到的余票数和程序写回的余票数。
  3. 用座位数、出票数和余票数的关系检查结果。解释调整时间和改变加锁范围分别改变了什么。

实验二 · 条件变量

通知发出后会发生什么

每个工作线程最多领取一项任务。主线程可以在任务入队后通知，也可以在队列为空时先发通知。观察收到通知的线程能否领到任务。

修改 02-queue/config.sh，保存后运行。

bash run.sh queue
下载条件变量实验包（ZIP）

配置参数

数值填整数，英文选项按表中写法填写，区分大小写。

条件变量：配置参数
参数与默认值 允许的取值 作用
WORKERS=11～8工作线程数。每个线程在一次运行中最多领取一项任务。
JOBS=10～8主线程一次放入队列的任务数。0 表示不放入任务。任务数超过线程数时，即使所有线程各取一项，也会有任务剩余。
EMPTY_NOTICE=00 / 10：放入任务前不发通知。
1：队列为空时先广播一次，等待 OBSERVE_MS 毫秒，再放入任务。这次提前通知始终使用广播，不受 NOTICE 影响。
NOTICE=broadcastsignal / broadcast放入任务后的通知方式。
signal：通知一个等待线程。
broadcast：通知所有等待线程。
WAIT=ifif / whileif：等待返回后直接尝试领取任务，不因队列为空而重新等待。
while：每次被唤醒后都重新检查；队列为空且尚未关闭时，继续等待。
OBSERVE_MS=300100～2000 毫秒放入任务后，主线程等待这么久再统计结果。若 EMPTY_NOTICE=1，提前通知到放入任务之间也等待同样长的时间。

EMPTY_NOTICE 决定是否提前广播，NOTICE 决定任务入队后的通知方式，WAIT 决定工作线程醒来后的行为。

操作与结果分析建议

需要完成的任务

  1. 让等待线程多于任务

    从一个线程、一项任务开始，先增加线程数，再增加任务数。找出出现和未出现 EMPTY_ATTEMPT 的配置。解释为什么任务够多时可能没有空取，再判断这能否说明等待逻辑正确。

  2. 在空队列时发通知

    恢复默认配置，只设 EMPTY_NOTICE=1。预测工作线程会怎样响应提前通知，以及稍后放入的任务是否还有线程领取，再运行核对。

  3. 比较 if 与 while

    分别恢复前两步中出现空取的配置，只把 WAIT 改为 while。观察线程醒来发现队列仍为空时，接下来会怎样。

  4. 比较单个通知和广播

    设置两个线程和两项任务，保持 WAIT=while、EMPTY_NOTICE=0。比较 signal 与 broadcast 下各线程的领取情况。若没有空取却仍有剩余任务，解释原因。

读懂程序输出

WAIT、WAKE 和 TAKE 分别表示等待、唤醒和领取。EMPTY_ATTEMPT 表示线程尝试从空队列取任务，下面简称“空取”。

SNAPSHOT 给出统计时的已领取数 taken、剩余数 queued 和累计空取次数 empty_attempts。主线程随后输出 CLOSE 并唤醒等待的线程退出。关闭后，工作线程停止领取任务。

看剩余任务时，先区分线程尚未醒来、醒来时没有任务，以及等待逻辑有误。需要时延长 OBSERVE_MS 再运行。

需要提交的材料

  1. 附上预测、完整配置和程序输出。覆盖任务少于线程数、提前通知，以及在这两种条件下 if 与 while 的对照。
  2. 对照两个线程、两项任务时的 signal 与 broadcast。记录 CLOSE 前的 taken、queued 和 empty_attempts。
  3. 解释线程收到通知后为何仍要检查队列，以及没有空取时为什么也可能有任务无人领取。

实验三 · 信号量

为什么可用资源越来越少

线程拿到信号量许可后才能使用资源。每轮发起申请的线程数等于资源池的初始容量。你可以让一部分线程在拿到许可后取消任务。同一次运行的各轮共用一个信号量。

修改 03-pool/config.sh，保存后运行。

bash run.sh pool
下载信号量实验包（ZIP）

配置参数

数值填整数，英文选项按表中写法填写，区分大小写。

信号量：配置参数
参数与默认值 允许的取值 作用
CAPACITY=21～8信号量的初始许可数。每轮发起申请的线程数也等于这个值；后续轮次不会自动补回缺少的许可。
ROUNDS=31～8一次启动后连续运行的轮数。各轮共用一个信号量；重新启动程序才按 CAPACITY 重新初始化。
CANCEL=00～CAPACITY每轮要取消的任务数。按取得许可的先后顺序，前 CANCEL 个成功申请的线程取消任务。成功申请数不足时全部取消；0 表示不取消。
WORK_MS=1000～500 毫秒取得许可后的模拟处理时间。所有线程尝试申请后，成功取得许可的线程都会等待这么久，包括随后取消任务的线程。0 表示不额外等待。
CLEANUP=leakleak / returnleak：正常完成时归还许可，取消任务时不归还。
return：无论正常完成还是取消任务，只要取得过许可，就会归还。

CANCEL 只影响已经取得许可的线程。申请失败的线程没有拿到许可，也没有许可可归还。

操作与结果分析建议

需要完成的任务

  1. 跟踪许可逐轮变化

    先运行不取消任务的配置，记下每轮结束时的可用许可数。增加 CANCEL，预测许可会在哪一轮耗尽。调整 ROUNDS 验证，并保存从申请成功到全部申请失败的输出。

  2. 增大容量

    固定 CANCEL，只增大 CAPACITY。先预测增加容量会怎样影响许可耗尽的轮次，再看结果是否支持你的预测。

  3. 缩短处理时间

    保持 CANCEL 和 CAPACITY 不变，只把 WORK_MS 改为 0。检查每轮结束时的可用许可是否恢复，区分暂时占用与结束后没有归还。

  4. 比较取消后的归还方式

    恢复此前出错的配置，只把 CLEANUP 改为 return。然后设置 CANCEL=CAPACITY，使所有取得许可的线程都取消任务，核对每轮结束时的可用许可数。

读懂程序输出

ACQUIRE 表示取得许可，EAGAIN 表示申请时已无可用许可。CANCEL 和 FINISH 分别表示取消任务和正常完成，两行都注明是否归还许可。

ROUND 中的 start_available 是本轮开始时的可用许可数。所有工作线程结束后，主线程临时取出许可进行计数，再全部归还。END 中的 available 是这次计数的结果。

每轮所有线程都尝试申请一次后，拿到许可的线程才开始等待。程序用普通代码分支模拟任务取消。算出本轮应剩的许可，再和下一轮的 start_available 核对。

需要提交的材料

  1. 附上预测、完整配置和输出。覆盖不取消任务、加入取消、增加容量、缩短等待、切换 return 和全部任务取消。
  2. 逐轮记录开始和结束时的可用许可数、申请成功数、取消数和申请失败数，比较预测和实际许可数。
  3. 引用 CANCEL 或 FINISH 行中的归还信息，解释许可为什么减少。说明增大容量、缩短等待和切换归还方式的不同影响。

实验四 · 事件驱动

程序为什么延迟处理快消息

程序从两条连接接收 slow 和 fast。可以让 slow 晚些发送，也可以延长它的处理时间。观察 fast 的延迟发生在接收前，还是接收后。

修改 04-events/config.sh，保存后运行。

bash run.sh events
下载事件驱动实验包（ZIP）

配置参数

数值填整数，英文选项按表中写法填写，区分大小写。

事件驱动：配置参数
参数与默认值 允许的取值 作用
SLOW_SEND_MS=00～2000 毫秒程序启动后，预定等待多久发送 slow。0 表示不额外推迟发送。
FAST_SEND_MS=1000～2000 毫秒程序启动后，预定等待多久发送 fast。它与 SLOW_SEND_MS 使用同一个计时起点，并不是相对 slow 的间隔。
SLOW_WORK_MS=00～2000 毫秒开始处理 slow 后额外等待的时间，用来模拟慢处理。0 表示不额外等待。fast 的处理不受这个参数直接控制。
IO=blockingblocking / epollblocking：先阻塞读取 slow，再读取 fast。
epoll：把套接字设为非阻塞，用 epoll 等待可读事件，读取已有数据的连接。
HANDLER=inlineinline / workerinline：接收线程直接处理消息，处理结束后才能继续接收。
worker：把处理交给最多两个工作线程，接收线程继续执行读取操作。

IO 决定怎样读取消息，HANDLER 决定哪个线程负责处理。两项可以组合。即使预设的发送时间相同，实际顺序也会受线程调度影响。

操作与结果分析建议

需要完成的任务

  1. 让 slow 晚到

    先运行默认配置。只推迟 slow 的发送，让 fast 先到，并逐步拉大发送间隔。预测并记录 fast 从发送到处理结束的耗时。保持同一组发送时间，只把 IO 改为 epoll，再测一次。

  2. 让 slow 处理得更久

    保持 IO=epoll、HANDLER=inline。让 slow 先到、fast 稍后到，再逐步增大 SLOW_WORK_MS。对照 fast 的发送、接收和开始处理时间，找出等待期间接收线程在做什么。

  3. 把处理交给工作线程

    保留上一步让 fast 明显延迟的配置，只把 HANDLER 改为 worker。检查 fast 能否在 slow 处理结束前完成，并用输出解释原因。

  4. 把工作线程和阻塞读取组合

    保持 HANDLER=worker。恢复第一步的发送时间，让 fast 先到，再把 SLOW_WORK_MS 设为 0、IO 设为 blocking。先预测 fast 还会不会等待，再运行验证。

读懂程序输出

SEND、RECEIVE、HANDLER_START 和 HANDLER_END 分别记录发送、接收、开始处理和处理结束的时刻，均从程序启动起算。SUMMARY 中的 latency_ms 是从记录发送时刻到处理结束的总耗时。

消息由独立线程按预设时间发送，实际发送时刻可能因调度而推迟。用 fast 的时间戳分别算出发送到接收、接收到处理结束的耗时。SLOW_WORK_MS 用等待模拟慢处理，写报告时要说明这一点。

需要提交的材料

  1. 附上各次预测、完整配置和程序输出。覆盖慢到达时 blocking 与 epoll、慢处理时 inline 与 worker，以及 worker 搭配 blocking 的对照。
  2. 记录 fast 的发送、接收、开始处理和处理结束时刻，计算接收前后的两段耗时并作比较。
  3. 对照 fast 等待期间 slow 的处理过程。解释改变读取方式和改变处理线程分别能减少哪段等待。
